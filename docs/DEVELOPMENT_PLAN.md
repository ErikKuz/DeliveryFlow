# Этапы разработки DeliveryFlow

Этот план описывает **результат каждого этапа человеческим языком**. Точные HTTP-поля и ответы задаются отдельно в OpenAPI; структура БД — миграциями Flyway. План можно уточнять после проверки очередного работающего сценария, не меняя задним числом уже применённые миграции.

Исходная точка: в репозитории уже есть Maven-проект на Java 21 и Spring Boot, первый [OpenAPI-контракт](../openapi/delivery-api.v1.yaml), черновая реализация создания доставки и [`V1__create_deliveries.sql`](../delivery-service/src/main/resources/db/migration/V1__create_deliveries.sql). Ниже перечислена **планируемая работа**, а не готовые возможности.

## Этап 1. Рабочая заявка на доставку

Доводим существующий `delivery-service` до запуска с локальным PostgreSQL. Flyway создаёт таблицу, сервис корректно принимает данные от заглушки MarketFlow, сохраняет одну доставку на `sellerOrderId` и возвращает результат по действующему контракту. Повтор одинаковой заявки не создаёт вторую запись; повтор с изменёнными данными даёт конфликт. Исправляем валидацию, ошибки и текущие проблемы компиляции и маппинга.

**Готово, когда:** новую заявку можно создать через REST, найти в БД, повторить без дубля и получить понятную ошибку для неправильного запроса. На этом этапе товар ещё не считается физически принятым.

**Основные инструменты:** Java 21, Maven, Spring Boot, Spring MVC, OpenAPI/Swagger, Spring Data JPA, Hibernate, PostgreSQL, Flyway. Тесты добавляем по мере реализации: JUnit 5, Mockito и Testcontainers для проверки работы с настоящим PostgreSQL.

## Этап 2. Логистические пункты и физический приём

Фиксируем ответ на вопрос, как товар попадает в Москву. Добавляем главный пункт, ограниченный справочник обслуживаемых городов России и местные пункты. Оператор подтверждает получение посылки московским пунктом; до этого посылка не доступна машине или курьеру. Правила России, начального состояния и адреса забора согласуем с первым OpenAPI-контрактом **до** изменения API или БД.

**Готово, когда:** система различает «заявка создана» и «товар принят», знает пункт назначения и не запускает маршрут для неподдерживаемого города без явного решения.

**Основные инструменты:** Spring MVC, JPA/Hibernate, PostgreSQL, новые Flyway-миграции. Spring Security подключаем перед открытием действий оператора и других ролей; права проверяются на сервере.

## Этап 3. Доставка внутри Москвы

После подтверждённого приёма московская доставка появляется только в ленте доступных московских курьеров. Курьер видит пункт и адрес покупателя, атомарно берёт доставку, начинает её и подтверждает вручение. Учитываем расчётное время последней мили, но один только таймер не делает доставку вручённой.

**Готово, когда:** два курьера не могут взять одну доставку, курьер другого города её не видит, а `DELIVERED` появляется только после подтверждения вручения.

**Основные инструменты:** Spring MVC, Spring Security для ролей курьера и оператора, транзакции JPA/PostgreSQL. Проверяем конкурентное назначение тестами.

## Этап 4. Межгород: машины, водители и рейсы

Добавляем свободные машины и водителей в Москве. Для доставки в другой обслуживаемый город либо атомарно резервируем доступную пару, либо оставляем заявку в очереди. Создаём отдельный рейс с временем отправления, расчётным прибытием и временем возврата. После подтверждения поступления в местный пункт доставка открывается курьерам этого города. Возврат машины живёт своей жизнью: посылка может быть вручена до возвращения автомобиля.

**Готово, когда:** одна машина и один водитель не получают два пересекающихся рейса; отсутствие свободной пары не блокирует запрос; машина вновь доступна только после завершённого возврата.

**Основные инструменты:** JPA/PostgreSQL и Flyway для отдельных таблиц, планировщик Spring для наступивших сроков. Сроки хранятся в БД; внутри HTTP-запроса не используется `sleep`. В учебном режиме автоматическое наступление событий явно помечается как симуляция.

## Этап 5. Виртуальные начисления

Для завершённой доставки создаём одну запись начисления курьеру; для завершённого рейса — одну запись водителю. Сохраняем тариф, применённый к конкретной работе, чтобы будущая смена тарифа не переписала историю. Повторная команда или событие не создаёт второе начисление.

**Готово, когда:** по каждой завершённой доставке и каждому завершённому рейсу есть не более одного соответствующего начисления, а виртуальный баланс можно вычислить из записей. Реальных денежных переводов нет.

**Основные инструменты:** PostgreSQL, JPA/Hibernate, Flyway, транзакции и ограничения уникальности.

## Этап 6. События и уведомления

После сохранения изменений публикуем факты о создании, прибытии, вручении и завершении рейса. Подписчики используют их для уведомлений и будущей передачи статусов MarketFlow; команды назначения курьера или машины по-прежнему проверяют актуальное состояние БД. Форматы событий описываем заранее, а публикацию делаем устойчивой к повторной доставке и сбоям между БД и брокером.

**Готово, когда:** событие не теряется после успешного изменения БД, повторное получение события не удваивает результат, а уведомление не мешает основной операции доставки.

**Основные инструменты:** Kafka, Spring Kafka, Apache Avro; при необходимости — паттерн transactional outbox. `notification-service` позднее можно написать на Kotlin, но это необязательно.

## Этап 7. Разделение приложения на сервисы

Только после работающего сквозного сценария выделяем самостоятельные части по ответственности: доставка, пункты, автопарк/рейсы, курьеры и начисления. У каждой части — собственные данные и миграции, без общих JPA-сущностей или прямого доступа к чужим таблицам. Простой синхронный поиск пункта можно выполнить через OpenFeign; резервирование машины — через gRPC с Protocol Buffers. Внешние клиенты обращаются через Gateway, сервисы обнаруживаются через Eureka. Для удалённых вызовов задаём тайм-ауты и правила отказа: сбой не может считаться успешным резервированием.

**Готово, когда:** разделённые сервисы сохраняют прежнее поведение доставки и выдерживают временную недоступность соседнего сервиса без ложных назначений.

**Основные инструменты:** Spring Cloud Gateway, Eureka, OpenFeign, gRPC, Protocol Buffers, Resilience4j. Caffeine допустим для стабильных справочников пунктов и тарифов, но не для списка свободных машин и доступных заказов.

## Этап 8. Запуск вместе и реальная интеграция

Когда DeliveryFlow работает самостоятельно, поднимаем его инфраструктуру через Docker Compose и подключаем MarketFlow вместо заглушки, не заставляя проекты совместно использовать одну БД. Проверяем полный путь заявки, машины, курьера и начислений, а также перезапуски и ошибки зависимостей. Выбираем источник и проверку Bearer-токенов для межсервисных вызовов и ролей пользователей.

**Готово, когда:** чистый запуск на другой машине разворачивает нужные сервисы и БД с миграциями, а MarketFlow обменивается с DeliveryFlow согласованными данными и статусами.

**Основные инструменты:** Docker, Docker Compose, Spring Security, JUnit 5, Mockito, Testcontainers. Совместимость версий Spring Boot и Spring Cloud проверяем перед подключением соответствующих зависимостей.

На **каждом** этапе сначала уточняем бизнес-правило и при изменении REST API обновляем OpenAPI, затем пишем реализацию, миграцию и проверки. Это позволяет двигаться небольшими работающими частями, а не подключать весь технологический стек одновременно.
